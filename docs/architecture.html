Huddle on ESP32

Huddle is a paper from Amazon Robotics (DARS 2026). Simple hexagon robots build a shape together. No robot has a map or a leader. Each robot knows its own six walls and gets two numbers from each neighbour. This project does the algorithm again in C, tests it on 160,000 shapes, and puts it on ESP32 boards.

1 · Software layers

One core, four users

All decisions are in core/huddle.c. It is about 300 lines of portable C99. It uses no heap and no global state. Each function is a pure function. Thus the same file runs in the simulator, in the tests, on the host and on the ESP32.

2 · One robot

Six walls, three states

Wall 0 is the front (F). The labels go counter-clockwise. Each wall has one status:

null: no robot can attach here. The cell behind it is not in the shape.
free: a robot can attach. Nobody is there yet.
occupied: a neighbour is attached.

Click a wall to change its status. The robot packs the six statuses into its 16-bit status word, two bits per wall.

3 · The algorithms

Decide once at docking. Decide again each step.

Alg 6 is the safety rule. Without it, 79% of trials leave a cell that no robot can reach. The test harness catches this, so it does not pass everything by default.
4 · Wire format

Two integers in a signed 18-byte frame

The paper gives the widths, 16 bits and 32 bits. It does not give the field layout. The layout below is my choice. The two words are still the full payload. A sequence number and a 64-bit SipHash-2-4 tag protect them. All fields are little-endian.

0–1 status word2–5 pose word6–9 seq10–17 tag = SipHash(key, sender MAC, receiver MAC, seq, payload)

5 · Docking on the bench

The arena tells each board who its neighbours are

Real robots sense contact on each wall. The boards have no wall sensors yet. The laptop runs arena.py. It keeps the true map and tells each board about each new contact. A board accepts a frame only from the MAC address bound to that wall.

The arena makes a new 128-bit session key for each run and sends it over USB. The board keeps it in RAM only. A frame that comes before its ATTACH line is dropped; the neighbour sends it again in the next step. Frames are signed, not encrypted. Positions are not secret.

6 · Results

What the Monte Carlo runs show

Each run uses 40,000 random hole-free shapes, 10 to 300 cells (mean 155.4). k is the number of robots that dock in one step. The checkers test reachability and holes after every step.

Lost messages

The paper expects each neighbour message to arrive each step. The harness drops and delays messages. Select what a robot must think about a neighbour it has not heard from yet.

7 · Attacks on the radio link

Replay is safe. Forgery is not.

ESP-NOW had a replay flaw: CVE-2024-42483 and CVE-2024-42484 (Nozomi Networks, 2024). An attacker can send old frames again, also encrypted ones. Before this change, the only check was the source MAC address, and a radio can fake it. The simulator now attacks the link in two ways.

Replay: send an old status word again

A wall only goes from free to occupied. An old word is "more free", so it can only add delay. All 20,000 trials finish, also at 100% replay.

Without a merge, signals go on and off: 731,873 withdrawn signals at 50% replay. The monotone merge keeps the highest status per wall. Then the count is 0.

free → occupied: acceptoccupied → free: ignorenull: never changes

Forgery: send a false word

Select a forgery rate. No authentication.

The merge stops replay. The tag stops forgery. A board drops each frame that fails the tag, or that has a sequence number it saw before.

Session key

Espressif advisory AR2026-005 (2026) shows a voltage glitch can get an AES key out of an ESP32-S3. The base ESP32 has no glitch detector. Espressif tells users to use short-life keys. Thus each run gets a new key, in RAM only.

Tests

test_node changes each byte of a frame, replays frames, and uses a wrong key, no key, a fake source and a wrong destination. Each one is dropped. The SipHash code passes the published test vectors.

open

No secure boot or flash encryption. The key goes over USB, which is trusted. Not tested on boards yet. Whether arduino-esp32 3.3.10 has the CVE-2024-42483 code is unconfirmed; the tag and sequence check do not depend on it.

A compiler bug

The first runs had deadlocks. The cause was the loop vectorizer in Apple clang 21 at -O2. It miscompiled one loop over the shape. A 25-line file shows it: -O0 prints -2 -1 2 3, -O2 prints -8 -4 8 8. The build now uses -fno-vectorize. make test checks that -O0 and -O2 give the same results.
